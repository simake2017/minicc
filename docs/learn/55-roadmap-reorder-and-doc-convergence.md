# 55. ROADMAP 重排与文档线收敛：让"下一批做什么"只有一个答案

> 定位：这一批**不改一行业语言代码**——它改的是**路线本身**与**写文档的规矩**。
> 一句话：**下一批做什么，必须在打开 ROADMAP 的第一屏就能看见；而 spec/design
> 只在接口/契约变更时才写。**
> 产物：`docs/ROADMAP.md` §0（执行序）+ §1（主线 K 详情）、
> `docs/constraints/06-文档骨架规范.md` §2.0（收敛规则）、
> `check-doc-standard.sh` 判据⑦（机器断言）+ 突变验证新增 4 项。

## §0 定位与能力清单

| 能力 | 状态 | 落在哪 |
|---|---|---|
| 路线图有**唯一入口**（执行序在第一屏） | ✅ | `docs/ROADMAP.md` §0 |
| 每个待办项带**实测现状**（不是照抄旧文档的过期结论） | ✅ | §0.1 / §0.2 / §1（6 项全部 clang++-18 探针实测） |
| 严重度有**明确序**（缺陷优先于特性） | ✅ | §0 开头「排序判据」两条 |

## 1. 理论背景

### 1.1 路线图的第一读者是"下个会话的自己"

编译器项目最容易出的两类毛病：**代码烂**与**方向乱**。前者有编译器有测试兜着，
后者没有——没人写单测能测出"下一批该做什么"，而它恰恰是最贵的浪费：
一个会话花三小时读完 ROADMAP，最后选了一条**别人已经排掉的**线。

本项目的 ROADMAP 当时正是这个病灶：文件按**批次先后**排列，顶上一眼望去
是十来个 ✅ 的已完成主线（类模板特化、decltype/SFINAE、多继承布局……），
而真正待做的散落在中段，末尾还有一段"⏭ 后续计划见 ROADMAP（主线 C → D → E → F）"
——那句话在主线 C/D/E 早已做完大半的情况下已经过期。

★ 由此得一条**通用判据**：**路线图的第一屏必须回答"下一批做什么"**，
否则历史越厚，路线图越没用。历史不是删掉，是**挪到存档段**。

### 1.2 严重度序：缺陷优先于特性

软件工程里对技术债排序的通行做法是**严重度 × 成本**（Boehm 的缺陷修复优先级矩阵）。
本项目一直用 `docs/BUGS.md` 的 severity 字段，但**待办清单**此前没有排序口径，
于是"缺一个特性"和"静默算错一个字段"看起来一样重。

本批把口径写死成一条序：

```
静默算错  >  静默不匹配  >  诊断不对（clang 也拒，只是文案不同）  >  功能缺失（clang 接受、minicc 拒）
```

★ 为什么"诊断不对"排在"功能缺失"之前：clang 也拒、只是文案不同 ⇒ 改文案即可，
成本低一个数量级；而 clang 接受、minicc 拒 ⇒ 要补一整条语义，最后做。
★ 更要紧的是把"**静默**"两个字放在最前：静默的缺陷**没有症状**，
不会被任何测试、任何日志、任何用户报告抓到——本项目已吃过多次亏
（B27 无可行候选退回首个 / B34 const 对象掉标量路径 / B46 析构槽靠子串判定）。

### 1.3 "缺口里的缺口"：方向错了，努力就白费

§2.2 的六项里有一项是**反的**：`别名模板的偏特化`。
旧文档把它列在"未做"清单里，读起来像"待实现"；但标准说它**非法**：

```
$ clang++-18 -std=c++20 -fsyntax-only p_alias.cpp
p_alias.cpp:2:28: error: partial specialization of alias templates is not permitted
```

`[temp.alias]/1` 的要害是：别名模板**不是新类型**，只有"解糖"没有"实例化"
（见 docs/learn/27）。既然没有类型，就没有"特化"这回事——
写出来是**非法程序**，正确行为是**响亮拒收**。

★ 这类条目的杀伤力在于：**后来的会话会照着"未做"两个字去实现它**，
做出一堆代码，然后被标准与 clang 双重否定。所以本批在 §0.2 单列一行把方向写死。
★ 通用教训：**待办清单里的每一项，都要先确认"补的是不是真的缺"**——
用 oracle 探针跑一遍，比读十遍文档可靠。

### 1.4 "该写文档"的判据：接口稳定性

`docs/specs/` 与 `docs/designs/` 的骨架来自 biz-dev-pipeline（约束 → spec → 设计 → 代码），
它回答的是"这次变更**怎么设计**"。但它没有回答"**这次变更值不值得走这套流程**"。

答案是接口稳定性：**契约变了，后来者需要知道"变了什么、为什么变"**，
而签字流程该落在**变更面**上；纯实现细节、纯缺陷修复、纯重构，写出来的东西
与代码不同步后就是负债。

## 2. 病灶与改法

### 2.1 改法：ROADMAP 变成三段式

```
§0 当前优先级（执行序）   ← 第一屏回答"下一批做什么"
   §0.1 批 0：缺陷与边界收口（2 项）
   §0.2 批 1~6：主线 K 模板线六项
   §0.3 降级区：语法面欠账（17 条，不占主线位）
   §0.4 暂不开新战线（5 条）
§1 主线 K：下一条主线的完整规格（每项六栏）
§2 既有主线的现状（存档；一段历史内容不删 —— 判据⑤ 资产）
```

★ **"一段历史内容不删"是硬约束**：守卫脚本判据⑤ 拿 git 基线比行数，
重排若顺手删段落就会判红。这条约束逼着改法落在"**挪位置 + 加索引**"上，
而不是"重写"——正好也是文档该有的纪律（G4 资产保留）。

### 2.2 主线 K 六项：现状全部实测（不是照抄）

| 项 | clang++-18 | minicc（实测） | 性质 |
|---|---|---|---|
| K-1 别名模板偏特化 / 显式特化 | **报错**（两种措辞各一） | 也拒，但文案是 parse 层的 `Expected '=' in using declaration` | 诊断不对 |
| K-2 偏特化模式的值位（`Box<int,N>`） | rc=0，选偏特化 | `type pattern 'N' does not match non-type argument '3'` ⇒ 退回主模板 | ★ **静默选错** |
| K-3 `template<auto V>` 的偏特化 | rc=0，选偏特化 | 同上一条 ⇒ 退回主模板 ⇒ `No member 'b' in class 'K_3Cint'` | ★ **静默选错** |
| K-4 模板模板形参：形参包 / 默认实参 / 嵌套 | 三种全 rc=0 | 三种全拒（文案各不相同，其中一种是自造的） | 缺特性 |
| K-5 类外定义特化成员 | rc=0 | `Expected ';' after global variable declaration` | 缺特性 |
| K-6 函数模板显式 NTTP 实参 | rc=0 | 响亮拒收，文案自造（`is not supported yet`） | 缺特性（诊断不对） |

★ **K-2 的关键细节**：偏特化模式里的**常量值位**（`Box<T,0>`）**早就支持了**
（docs/learn/34 §3.3 打的地基）——旧文档说的"NTTP 特化模式：Parser 直接报错"已经过期。
真正缺的是**待推导名形态**（`Box<int,N>`：N 是偏特化自己引入的形参）。
★ 同一批里两处"旧结论已过期"，说明：**待办清单会腐烂**，腐烂了就必须重新探针，
不能照抄——这是本批把"实测现状"写进 ROADMAP 的直接理由。

## 3. 文档线收敛规则

### 3.1 规则本体（`docs/constraints/06-文档骨架规范.md` §2.0）

一句话：**`docs/specs/` 与 `docs/designs/` 仅在【接口/契约变更】时才写。**

| 场合 | 写不写 | 去哪写 |
|---|---|---|
| 跨模块契约变更（`include/**`、模块间接口、诊断文案契约、命名规则契约） | ✅ 写 | spec → design |
| 新增语言特性 | ⬜ 不写 | `docs/learn/NN`（理论 + clang 对照 + 实验） |
| 缺陷修复 | ⬜ 不写 | `docs/BUGS.md` 一条 + 回归用例 |
| 纯重构 | ⬜ 不写 | 归档类（过程记录） |
| 规则/标准变更 | ⬜ 不写 | `docs/constraints/**` |
| 只改日志键名 / 只改测试 | ⬜ 不写 | — |

★ **没有豁免通道**：要留痕就写契约；确实没有契约变更，就别写 spec/design。
豁免通道（"本篇无契约变更"）会把规则架空——它等于给"随手补两份文档"发了通行证。

### 3.2 规则成机器断言：判据⑦

```
判据⑦ 契约变更点：每份 spec / design 必须有一行「契约变更点」，
                 写明哪一个契约变了（include/** 的某个头 / 某个诊断类别 /
                 docs/constraints/** 的某条规则 / 某个 BUGS 编号）。
                 写不出来 ⇒ 这份文档不该存在 ⇒ 判红。
```

★ 判据只查"**有没有声明**"，不查"声明得对不对"——
与判据⑥ 同理：它挡得住"忘了写"，挡不住"写错了"，后者要靠人读。
★ 存量 13 份 spec/design 全部补上该行。其中
`parser-stage-name-recognition`（`NameRegistry`）那一行注明
"该契约已于 Stage 3 批 2+3 整类撤销，见 docs/learn/52"——
**历史文档不必装作契约还在**，判据⑦ 记的是"当时变了哪个契约"。

### 3.3 为什么必须落成机器断言

本项目已有两条同款经验（主线 J 第 6 项）：
**注释标准**与**文档骨架标准**都先写成规范、再写成守卫脚本 + 突变验证。
理由很直白：**写在纸上没人查就会腐化**。收敛规则若只停在 prose，
半年后就是"文档太多了"的一句抱怨，而不是一条能判的规矩。

## 4. 可复现实验命令

```bash
# ① 守卫脚本（7 条判据；判据⑦ 缺一行即红）
./check-doc-standard.sh

# ② 突变验证（每条判据两次实测：引入违规必须红 + 放松判据必须绿）
./verify-doc-mutations.sh          # ⇒ 30/30

# ③ 六项模板欠账的现状探针（clang++-18 是 oracle）
cat > /tmp/k2c.cpp <<'EOF'
template<class T, int N> struct Box { int v; };
template<int N> struct Box<int, N> { int w; };
int main(){ Box<int,3> b; return 0; }
EOF
clang++-18 -std=c++20 -fsyntax-only /tmp/k2c.cpp   # rc=0（选偏特化）
./build-linux/minicc /tmp/k2c.cpp                  # ⇒ "type pattern 'N' does not match …"

# ④ K-1 的方向核对（clang 明确说"非法"）
cat > /tmp/p_alias.cpp <<'EOF'
template<class T> using Vec = T*;
template<class T> using Vec<T*> = const T*;
int main(){ return 0; }
EOF
clang++-18 -std=c++20 -fsyntax-only /tmp/p_alias.cpp
# ⇒ error: partial specialization of alias templates is not permitted
```

## 6. clang 源码对照表（本批新增锚点，均已在本地语料 grep 核实）

| clang 位置 | 对应本批哪一处 | 简化了什么 |
|---|---|---|
| `clang/lib/Parse/ParseDeclCXX.cpp:Parser::ParseUsingDeclaration` | K-1 的诊断出处（`err_alias_declaration_specialization`） | clang 在**解析期**就判"别名模板不能特化"；minicc 目前没有这个判据 |
| `clang/include/clang/Basic/DiagnosticParseKinds.td:err_alias_declaration_specialization` | K-1 的**逐字文案**来源（`%select{partial specialization\|explicit specialization\|explicit instantiation}`） | minicc 只需前两种措辞 |
| `clang/lib/Sema/SemaTemplate.cpp:Sema::CheckTemplatePartialSpecialization` | K-2 / K-3 的形态校验面 | clang 把"偏特化模式是否合法"与"模式能否匹配"分成两处；minicc 暂只有后者 |
| `clang/lib/Sema/SemaTemplate.cpp:Sema::CheckTemplateTemplateArgument` | K-4 的模板模板实参签名匹配（learn/33 已对齐该口径） | clang 逐位比对内层形参表；minicc 已有逐位签名表，缺形参包与默认实参 |
| `clang/lib/Sema/SemaTemplateDeduction.cpp:Sema::DeduceTemplateArguments` | K-6 的显式实参路径（显式实参不走推导） | minicc 目前对函数模板的显式 NTTP 实参一律拒 |

★ 本批**没有搬任何 clang 代码**，只取诊断措辞与判据形状（红线：只移植算法）。

## 7. 边界与未做

1. **判据⑦不查"声明得对不对"**：契约点写错了照样绿（与判据⑥ 同理，需人读）。
2. **收敛规则管的是"spec/design"，管不了 learn 的体量**：learn 文档本就有膨胀倾向
   （本批自己新增的第 55 篇就是个例子），但 learn 是**学习产物**，是交付三件套之一，
   不在收敛规则的射程内。
3. **§0.3 降级区里的 17 条**没有逐条写清"做完要多久"——它们本就是"等被依赖时再做"的项。
4. **主线 K 六项的落点只写到"哪个文件、哪套引擎"一级**，还没到任务分解级
   （每项开批时再按 CLAUDE.md 的 `docs/prompt-template-deduction.md` 格式产出）。
5. ★ **本批没写新的 learn 编号之外的学习产物**：按收敛规则，
   纯规则/规划变更不产出 spec/design；学习产物就是本篇。

## 8. 真实版多做了什么、为什么

**多做了三件"没被点名"的事**：

1. **六项模板欠账全部用 clang++-18 重新探针**（原计划只是"排个序"）。
   原因：旧文档里的"NTTP 特化模式：Parser 直接报错"**已经过期**
   （常量值位早就支持了），照抄会把已完成的事再排一遍。
   探针还揪出 **K-1 的方向是反的**——它不是缺口，是"该拒没收准"。
2. **把收敛规则做成了机器断言（判据⑦）+ 突变验证 4 项**（原计划只是写一条规则）。
   原因：本项目已有的两条标准（注释、文档骨架）都是"规范 + 守卫 + 突变验证"三件套；
   只写规则不写断言，等于把纪律寄托在记忆上。
3. **存量 13 份 spec/design 全部补「契约变更点」行**（原计划没提）。
   原因：判据⑦ 若只对新文档生效，存量文档就会成为"豁免区"，
   规则立刻出现后门——那还不如不写这条规则。

**没做什么（有意）**：没有为了"显得有产出"而新增编译器特性；
本批**零代码改动**（判据⑦ 与突变验证脚本是本批唯一的"代码"），
`ctest` 与 `logdiff` 因此保持全绿、零漂移——这是应有结果。
