# 06-文档骨架规范（唯一权威）

> 上级：[05-文档标准与冲突裁决](05-文档标准与冲突裁决.md)（裁决"为什么这么分"）
> 本文件裁决**"具体长什么样"**：每个文档族的骨架、必填节、裁剪规则。
> 落库：2026-11-02 ｜ 触发：全项目文档按新标准重整（L1~L9）。

---

## 0. 通则（所有族共用）

| # | 规则 | 说明 |
|---|---|---|
| G1 | **一文档一主题** | 一个主题一份文档；子主题用子目录 + `00-总览.md` 索引 |
| G2 | **头部四行钉死** | 读者 / 审法 / 名词版本 —— 技术文档与开发文档必填 |
| G3 | **变更记录表** | 每份文档一张；改任何内容**先改这里**（tech-doc 变更纪律） |
| G4 | **资产保留** | 整改只**增**骨架节，不删现有正文；重写只允许"同一段逻辑挪位置" |
| G5 | **内容资产不截断** | 日志、汇编、探针输出、命令**原样保留**（wiki-postmortem 铁律） |
| G6 | **占位符零容忍** | `xx_` / `<type>` / `..._` 一律为 0（占位符是"没写完"的信号） |
| G7 | **内部名不上图** | 图上不许出现 `m_pos` 这类私有符号；**允许** clang 的 `文件:符号` 对照坐标（见 05 §C2） |
| G8 | **确定语气** | 描述本项目行为用确定语气；描述上游必须标版本（clang++-18 / 2026-07 上游）（见 05 §C3） |

## 1. 技术文档族（tech-doc 骨架 · 模块卡规格）

**归属**：`docs/business/**`、`docs/cmake-build-system.md`、`docs/toolchain-search-paths.md`、
`docs/escape-and-file-reading.md`、`docs/make-tutorial.md`、`cpp-compilation-lifecycle/tutorial.md`、
`demos/README.md`。

### 1.1 ★ 模块卡规格（`docs/business/**` 的 40~80 行卡片）

**技术文档的完整骨架是给"业务规格"用的；本项目的业务文档是 40~80 行的模块卡，
把 §1~§12 全铺开会变成噪音。按 tech-doc 自带的【瘦身规则】
（"这一节删掉，人会不会做错？不会就删"）裁剪成下述骨架。**

```markdown
# <域>.<序号> <主题> —— <一句话职责>

> 上级：<00-总览 链接> ｜ 相关：<learn 文档 / BUGS 编号>
```

**裁剪规则**：

| 情况 | 处置 |
|---|---|
| 该模块**不产出诊断**（如"词法"里的字面量切分） | §3 写「本模块不产生诊断文案（错误在下游阶段报）」一行，**不硬凑** |
| 该模块**无日志输出** | §5 写「本模块不打日志」一行 |
| 该模块**确实有**多于 3 条 Out of Scope 的历史遗留 | 列全，不截断 |
| 该模块是**总览页**（`00-总览.md`） | 只补四行头部 + 变更记录 + §4 Out of Scope + §5 观测点（其余节按内容裁） |

## 3. 学习文档族（mini-restore 三段式 → 映射进项目骨架）

**归属**：`docs/learn/NN-*.md`。

★ **不并行两套骨架**（05 §C5）：项目 CLAUDE.md 要求的五项是主干，
mini-restore 三段式**映射**进去。

| mini-restore | 落到项目骨架 |
|---|---|
| ① 我实现了什么 | **新增 §0 定位与能力清单** |
| ② 真实源码对照 | 已有「clang 源码对照表」——**列名对齐两列式**（clang 符号 ↔ 本实现位置） |
| ③ 真实版多做了什么、为什么 | 已有内容**提升为独立小节**「§N 真实版多做了什么、为什么」 |
| ④ 踩坑记录 | 已有踩坑史 / BUGS 引用——**统一小节名** |
| ⑤ 演进记录 | **新增文末「演进记录」表** |

### 3.1 目标骨架

```markdown
# <NN>. <主题>（<一句话>）

> 关联：<spec / design / BUGS 编号 / 上一节>

## §0 定位与能力清单          ← ① 新增

<一句话定位> + 一张能力表>

| 能力 | 一句话 | 状态 |
|---|---|---|

## §1 理论背景                ← 原有，保留
## §2 设计决策                ← 原有，保留
## §3 真实版多做了什么、为什么   ← ③ 由 §2 里的"简化了什么"提升独立
## §4 clang 源码对照表         ← ② 列名改两列式
## §5 可复现实验命令           ← 原有，保留
## §6 关键过程 ASCII 图        ← 原有，保留

## 演进记录                    ← ⑤ 新增
| 日期 | 改了什么 | 为什么 |
```

★ **节号不强制**：现有 learn 文档的章节名各不相同，
**按"有没有该内容"补节，不为凑节号重排正文**。
凡"能力清单 / 真实版多做了什么 / 演进记录"三块缺任一 ⇒ 判不合格。

### 3.2 §0 定位与能力清单的写法

- 一句话定位：**这个机制解决什么问题**，不写"本节讲…"（那是复述标题）
- 能力表每行：能力（对应标准里的哪个概念）｜一句话｜状态（已实现 / 部分 / 未做）

## 4. 复盘文档族（wiki-postmortem 骨架）

**归属**：`docs/BUGS.md`、`docs/PITFALLS.md`、`docs/NOTES-阅读笔记.md`。

### 4.1 文件级 frontmatter（三份都要）

```markdown
---
title: <标题>
date: 2026-11-02
category: compiler
tags: [<tag>, ...]
type: <index | postmortem>
severity: <high | medium | low>
status: <active | maintained>
related: ["[[<链接>]]", ...]
---
```

★ `related` 用 `[[wikilink]]` 形式（llm-wiki 规范），指向本仓库内的相对路径。

### 4.2 条目级元数据（BUGS.md 的 38 条）

每条缺陷的标题下加**一行行内元数据**（不是 YAML 块 —— 38 个块会毁掉可读性）：

```markdown
## B20 vtable 槽里的符号名与定义点不同源

- severity: high ｜ status: fixed ｜ related: docs/learn/13, docs/learn/17

| 项 | 内容 |
|---|---|
| 现象 | ... |
| 根因 | ... |
| 修法 | ... |
| 回归 | ... |
```

★ **B 编号不变**（全项目 200+ 处引用键）。条目小节名统一为：
`现象 / 根因 / 修法 / 回归 / 教训`（缺哪块写"无"，
**不许删掉已有内容**）。

## 5. 端到端线文档族（line 骨架）

**归属**：`docs/lines/**`（新建）。

```markdown
# 线：<一次端到端子流程>

- 读者：<谁>
- 审法：<一句话>
- 名词版本：v1

## 变更记录
| 日期 | 版本 | 改了哪条 |

## §1 这条线是什么（入口 + 结局）
## §2 走线五步法的结论（一句话一跳的表）
| # | 跳 | 落在哪个文件:函数 | 这一跳干了什么 |
## §3 逐跳详解（每跳：源码锚点 + 做了什么 + 为什么）
## §4 断链点（动态派发处：列出全部实现 + 说清选了哪支）
## §5 分叉与旁路（可选分支）
## §6 观测点（这条线上打了哪些日志键）
```

★ line 的红线：**线是"跑出来的调用链"，不是目录导览**；
每跳必须有**源码锚点**（文件 + 函数名 + 一句话职责），凭印象写 = 没读。

## 7. 机器断言

`check-doc-standard.sh`（与 `check-comment-style.sh` 同款思路）：

| 判据 | 内容 |
|---|---|
| ① 头部 | 技术/开发/线文档必须有「读者 / 审法 / 名词版本」三行 + 变更记录表 |
| ② 骨架节 | 技术文档必须含「Out of Scope」与「观测点」两节；learn 文档必须含「能力清单」「真实版多做了什么」「演进记录」三块 |
| ③ 元数据 | BUGS.md / PITFALLS.md / NOTES 顶部必须有 YAML frontmatter；BUGS.md 每条必须有 severity/status/related 行 |
| ④ 占位符 | 全文不得出现 `xx_` / `<type>` 占位 |
| ⑤ 资产 | 文件行数不得减少（防"重写时丢内容"）——以 git 基线为准 |
| ⑥ 引用可达 | 文档里 `src/….cpp:N` 形式的源码引用：文件必须存在（按 2026-10-29「src 按 clang 分域搬移」的别名表解析）且行号不得越界 |

★ **判据⑥ 补记**（2026-11-02 追加）：①②③⑤ 管的是"骨架与体量"，**管不了
"文档说的和代码对不对"**。一次实测就抓出 **38 处不可达引用** —— 全部是
「src 按 clang 分域搬移」（commit 1d7551e）之后的**旧路径**
（`src/codegen.cpp` / `src/parser.cpp` / `src/semantic_analyzer.cpp` …）。
⇒ 别名表把"搬移前写的路径"解析到搬移后的文件（历史文档里那些路径是**有意保留**的
"成文时的路径"），真正写错的路径则无处遁形。
★ 这条判据的边界：**只验"引用能不能落到某个文件"**，验不了"这一行还对不对" ——
后者要靠人读（判据⑥ 只能挡住路径漂移，挡不住语义漂移）。

**突变验证**：同 `verify-comment-mutations.sh` 的做法，
每条判据两次实测（引入违规必须红、放松判据必须绿）。
