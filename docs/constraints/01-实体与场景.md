# 01-实体定义法与实体-场景矩阵（minicc 版）

> 编译器项目的"业务对象" = 管线各阶段产生/消费的语言名字与判定数据结构。
> 视角是**语言语义**（这个名字是什么、在哪一层当真），不是物理存储
> （某个 map、某张表）。存储只是实体的落点。

## 1. 实体定义模板（spec §1 概念里的每个实体照此写）

````text
实体：<业务名>
一句话：<20 字以内的语义定义，禁止出现存储名词（map/表/字段）>

业务属性（jsonc 定义，字段逐个钉死；有嵌套就原样展开，禁止拍平成表）：

```jsonc
// 实体：<业务名>   落点：<哪个阶段的哪个成员>
{
  "field": "示例值",   // 业务含义；空值/异常语义；谁写谁读
}
```

落点：<哪个阶段持有；一张主结构一个实体>

在哪些场景起作用：
  · 场景A：充当什么角色（如"判定依据"）
  · 场景B：……
````

## 2. 实体-场景矩阵（业务全景）

```text
                         场景1 parser 名字识别   …（新业务往右加列）
实体 名字登记表              ✓ 主角
```

作用：新需求进来先在矩阵里找位置——找不到对应实体 = 要先补实体定义；
实体行里没有场景 = 僵尸实体，要么删要么写清为什么留。

## 3. 落点对应规则

1. **一个实体一个主结构**，主键 = 语言名字的书写形（不是自增 id）。
2. 字段语义写在**实体定义处**（spec/本文档），落点结构只是它的投影；
   改结构先改定义。
3. 同名不同义的字段必须拆位（如一个名字的 type 位与 value 位是两个
   分类位，禁止一个布尔两种解释——C++ 里 `int S; struct S;` 合法并存）。
4. 分类/状态字段必须配**穷举表**（哪些位、各什么含义、谁置位），
   散落的 is_xxx 布尔是分类腐烂的开始。

## 4. 实体的粒度判据

- 一个实体 = 编译器作者嘴里**一个名词**（"这个名字""这张登记表""这个蓝图"）
- 拿不准 → 按"它有没有自己的生命周期和写入时机"判：有 = 实体；
  没有 = 别的东西的属性
