## 2. 冲突裁决表（逐条）

### C1 ⚠ 最高优先：tech-doc「不拆 spec + design 两份」 ⟷ biz-dev-pipeline「约束 → spec → 设计 → 代码」

| | |
|---|---|
| **冲突** | tech-doc 总原则 1 明文「不拆 spec 文件、设计文件两份，文档内部用『第一部分/第二部分』分界」；biz-dev-pipeline 正是两份；项目现有 4 spec + 3 design。 |
| **裁决** | **tech-doc 不适用于 spec/design 族**。项目保留"spec 一份 + design 一份"（biz-dev-pipeline 形态）。 |
| **依据** | P2（一个族一个技能）+ P1（项目既有纪律：docs/specs + docs/designs 已签字归档，CLAUDE.md 与 ROADMAP 引用它们）。tech-doc 的"不拆两份"针对的是**业务需求文档**，不是**变更计划文档**。 |
| **落地** | spec / design 两份的结构不动；只对齐 biz-dev-pipeline 的**字段名与节名**（见 C15）。 |

### C2 tech-doc「说人话、图上不许出现函数名」 ⟷ 编译器技术文档必须写 Pass 1/2/3、TokenCheckpoint

| | |
|---|---|
| **冲突** | tech-doc 自检表第 5 条：「业务术语：状态写『下载中』，不写 downloading ｜ **函数名/变量名上图**」为打回项。但编译器技术文档的"业务术语"就是**语言标准术语**（实参推导 / SFINAE / 两阶段查找），且对照坐标（clang 的 `Parser::TryAnnotateTypeOrScopeToken`）是本项目的**核心资产**。 |
| **裁决** | **在编译器语境下重述 tech-doc 的术语判据**（本条即重述，写死不再讨论）：<br>· **业务术语** = 语言标准术语（`[temp.deduct]` 的"实参推导"）+ 本项目判据名（"判据单点""名字即身份"）<br>· **内部名** = 本项目私有实现符号（`m_pos`、`m_currentClassName`、`m_currentNamespace`）—— **这些上图禁**<br>· **对照坐标** = clang 的 `文件:符号` —— **允许上图**（它是"对照坐标"不是"内部名"，且与注释标准同源） |
| **依据** | P3（clang 对照表是资产）+ 注释标准的既定口径（「要么回答为什么这样设计，要么给出对照坐标，要么提供可运行 demo」）。 |
| **落地** | 写进 `docs/constraints/04-注释规范.md` 的姊妹条款，供后续所有技术文档引用。 |

### C3 tech-doc 自检「无模糊词：大概/可能/视情况/尽量/一般 = 0」 ⟷ 描述上游 clang 行为时"可能/一般"是准确表述

| | |
|---|---|
| **裁决** | 该自检**只对"本项目自己承诺的行为"生效**。对上游 clang 的行为描述**不生效**——上游行为随版本变，写死反而是错的。<br>**替换纪律**：描述本项目行为 ⇒ 确定语气；描述上游 ⇒ **标版本**（`clang++-18` 探针实测 / 2026-07 上游语料）。 |
| **依据** | P3 + 项目 CLAUDE.md「语义 oracle：任何新特性先跑 clang++-18 确认预期」——oracle 是**版本化的**，文档必须带上版本。 |
| **落地** | 技术文档的自检表按此二分，逐份核对。 |

### C4 wiki-postmortem「YAML frontmatter 在文件顶部（per-document）」 ⟷ BUGS.md 单文件 38 条

| | |
|---|---|
| **冲突** | frontmatter 是**文件级**的；BUGS.md 一份文件装 38 条缺陷，无法 38 份 frontmatter。用户已拍板"保留单文件，每条补 frontmatter 字段"。 |
| **裁决** | **双层元数据**：<br>① **文件级**：BUGS.md / PITFALLS.md / NOTES-阅读笔记.md 顶部各加**一份**规范 YAML frontmatter（`title` / `date` / `category` / `tags` / `type` / `severity` / `status` / `related`）——满足 wiki-postmortem 的规范 YAML 要求<br>② **条目级**：每条缺陷用**行内元数据行**（不是 YAML 块，避免 38 个块破坏可读性）：<br>`- severity: high ｜ status: fixed ｜ related: docs/learn/13, docs/learn/17` |
| **依据** | P2（一个族一个骨架）+ wiki-postmortem 的 frontmatter 规范只约束"文件"，条目级用行内元数据不违反它。 |
| **落地** | 三份文件加文件级 frontmatter；38 条缺陷逐条补条目级三字段。 |
