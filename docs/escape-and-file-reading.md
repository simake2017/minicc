# 文件读取 vs 转义转换：编译器到底"在哪一步"把 `\n` 变成真换行

> 测试里 `"#define N \\\n10 ..."` —— 实际存储时 `\n` 是不是就已经是真换行？

## 第一部分：概要设计（这一块对外承诺什么）

### §1 概念

#### 1.1 实体

| 实体 | 是什么 | 在哪些场景起作用 |
|---|---|---|
| **源文件字节** | 磁盘上的原始字节序列；此时 `\n` 还是"反斜杠 + n"两个字符（`5c 6e`） | 一切开始的地方 |
| **缓冲区** | 整文件读进内存后的字节副本；**与磁盘逐字节相同** | 阶段 1~4 全程 |
| **翻译阶段** | C/C++ 标准 [lex.phases] 定义的 8 个有序步骤；每个阶段只干一件事 | 决定"哪一步做什么" |
| **转义序列** | 字面量内部的 `\n` `\\` `\"` 等；**只在字面量内部有意义** | 阶段 5 |
| **文件栈** | `#include` 嵌套时保存"（当前缓冲区, 当前位置）"的栈 | 阶段 4 |
| **哨兵字节** | 缓冲区尾部额外 pad 的若干字节，命中即停，省掉每字符一次边界判断 | 扫描阶段提速 |
| **行号表** | 文件偏移 → 行号的映射表；报错时才查 | 诊断阶段 |

#### 1.2 名词

| 名词 | 一句话（大白话） | 在哪出现 |
|---|---|---|
| 读取 | 纯字节搬运，零转换 | 阶段 1 |
| 转义翻译 | 把字面量里的 `\n` 变成字节 `0x0A` | 阶段 5 |
| 行拼接 | 删掉源码里"反斜杠 + 换行"这一对，让下一行接上来 | 阶段 2 |
| 文件栈 | include 嵌套的进出栈 | 阶段 4 |
| 惰性行号 | token 只存"哪个文件、第几个字节"，要报错时再回头查行号 | 诊断 |
| 哨兵字节 | 缓冲区尾部多 pad 的字节，作用是"读到它就停" | 扫描 |

### §2 正常流程

**整体流程图**（方框图）：

```
┌────────────────────────────────────┐
│ 磁盘上的源文件                      │
│   \n = 5c 6e（两个字符，不是换行）   │
└──────────────────┬─────────────────┘
                   │ 读取：纯字节拷贝，零转换
                   ▼
┌────────────────────────────────────┐
│ 缓冲区（字节原封不动）               │
│   阶段 2 行拼接 / 阶段 3 分词+注释剥离│
│   阶段 4 宏展开、#if 求值、#include  │
│   —— \n 仍然是 5c 6e                │
└──────────────────┬─────────────────┘
                   │ 阶段 5：字面量内部的转义翻译
                   ▼
┌────────────────────────────────────┐
│ 字面量的值                          │
│   \n = 0x0A（真换行生效）            │
└────────────────────────────────────┘
```

**步骤**：

1. **整文件读进缓冲区**。【为什么】真实编译器都这么做——文件只是"往缓冲区灌数据的来源之一"，逐字符流式读没有好处。
2. **阶段 2 做行拼接**：删掉"反斜杠 + 换行"这一对。【为什么】这是让多行宏定义能写在一处而语法上仍算一行的机制。
3. **阶段 3 分词 + 剥注释**；**阶段 4 做宏展开、`#if` 求值、`#include` 并合**。做完这些，`\n` 仍是两个字符——**这是正确行为**。
4. **阶段 5 才做转义翻译**：且**只对字面量内部**做。【为什么】字面量之外的 `\n` 是两个标识符字符，没有任何转义含义。
5. **诊断阶段用惰性行号**：token 只记"哪个文件、第几个字节"，报错时才回头查行表。

★ **当前实现落点**（2026-11-02 补骨架时核对源码；正文那张阶段表写于阶段 5 落地之前）：

| 阶段 | 本项目落点 | clang 对照坐标 |
|---|---|---|
| 阶段 1~4 | `src/lex/preprocessor.cpp:Preprocessor::processFile` → `Preprocessor::processText` | `clang/lib/Lex/PPDirectives.cpp:Preprocessor::HandleDirective` |
| 阶段 5 | `src/lex/lexer.cpp:Lexer::scanString` / `Lexer::scanChar` | `clang/lib/Lex/Lexer.cpp:Lexer::LexString` / `Lexer::LexCharConstant` |

### §2.5 更新对照

本主题**有写契约**：同一个字面量在"读完"和"翻译完"两个时刻的字节形态不同。
下面的对照直接取自正文「两个场景，字节级对比」一节的实测 hexdump。

改前（刚读进缓冲区 / 预处理输出里）：

```jsonc
{
  "阶段": "读取完成（阶段 1~4 之后）",
  "源码片段": "char *s = \"a\\nb\";",
  "字面量正文的字节": "61 5c 6e 62",   // a 反斜杠 n b —— \n 仍是两个字符
  "含义": "反斜杠 + n，还没有任何转义含义"
}
```

改后（阶段 5 翻译完）：

```jsonc
{
  "阶段": "阶段 5（字面量扫描时翻译）",
  "字面量正文的字节": "61 0a 62",        // ← 改：5c 6e 变成 0a
  "含义": "真换行生效；CodeGen 可直接把它嵌进 .rodata"
}
```

★ 同一件事在"编译测试文件的那一方"还差一跳：磁盘上 `\\\n` 是**四个**字节
`5c 5c 5c 6e`（三个反斜杠 + n），g++ 在翻译阶段 5 把它变成 `5c 0a`
（一个字面反斜杠 + 真换行）烧进二进制的 `.rodata`；**运行时 `std::string` 只是拷贝已经转好的字节，零转换**。

### §3 异常处理

| # | 异常（现象） | 如何处理 | 可重试 |
|---|---|---|---|
| 1 | 词法已经翻译过转义，日志回吐时直接打印原文 → **一行日志被裸换行截断**，后面的内容错位 | 回吐前先用 `escapeCharText` 把已翻译的字符重新转义成可打印形式（落点：`src/parse/parser.cpp:escapeCharText`，demo：`escapeCharText("\n")` ⇒ `"\\n"`） | 否——打印路径写错 |
| 2 | 字符串字面量缺闭引号 → `Unterminated string at 1:1` | [lex.string] 要求字符串在同一行内终结；补上闭引号 | 否——源码写错 |
| 3 | 空字符字面量 `''` → `Empty character literal at ... (C++ 不允许 ''，见 [lex.ccon])` | 源码写错 | 否 |
| 4 | 未知转义（如 `\x41`、`é`）→ 本项目**宽容处理**，反斜杠与后随字符原样保留 | 与 clang 不同（clang 会报错）；要对齐需扩翻译表（见 §4「Out of Scope」） | 否 |
| 5 | 以为预处理输出里的 `\n` 已经是真换行，据此写判断 | 记住"读"与"转"是两件事：预处理输出里 `\n` 永远是两个字符；转义翻译只发生在字面量扫描时 | — |

### §4 Out of Scope

- **阶段 6~8 的完整实现**：字符串字面量拼接（阶段 6）、预处理 token → C++ token（阶段 7）、翻译单元合并与外部链接（阶段 8）——正文那张表已经标了"未做"，本篇不展开。
- **Unicode 源字符集与 BOM 的处理**：阶段 1 假定"UTF-8 纯 ASCII 子集够用"，多字节字符集转换不在本文范围。
- **`\xNN` / `\uNNNN` 等十六进制与通用转义**：本项目翻译表目前只收简单转义，扩展路径见 §3 第 4 条。
- **多字符字面量的取值规则**：`'ab'` 取值由 Parser 按"末字节在前"的常见实现决定，本文不讨论其标准地位（implementation-defined）。
- **mmap 的实现细节**：只在"真实编译器怎么做"的对比表里出现，不讲页映射与缺页中断。
- **哨兵字节的收益量化与向量化扫描**：只讲"为什么可以省掉边界判断"，不讲 SIMD 扫描。
- **行号表的数据结构选型**：只讲"惰性查行号"这一条原则，不讲具体表结构。

### §5 观测点

| 时机 | 看的键 / 命令 | 看到什么算正常 |
|---|---|---|
| 怀疑源码里的 `\n` 不是真换行 | `xxd <file>` 或 `hexdump -C <file>` | `5c 6e` = 反斜杠 + n（**不是** `0a`）；`5c 5c 5c 6e` = 三个反斜杠 + n |
| 怀疑预处理把转义提前做了 | `minicc -E <file>` | 输出里 `\n` 仍是 `5c 6e`——**这是正确行为** |
| 看字面量最终被翻译成了什么 | 编译日志里的 `[parse:literal] '<字面量>' ⇒ 字符码点 <值>` | 码点是翻译后的数值（`'a'` ⇒ 97） |
| 看模板实参位上的字符字面量 | `[parse:targ] ★ non-type argument (NTTP): char literal '<转义后的可打印形式>' (<值>)` | 打印出来的形式是**已转义**的（`\n` 印成 `\\n`），不是裸换行 |
| 看预处理是不是把头并进来了 | 预处理输出里的 `# <行号> "<文件名>"` 行号标记 | 每个来源文件都有标记，位置对得上 |

## 第二部分：详细设计（怎么做）

### §6 整体流程图

分解视角：把"读进来"拆成四个子流程，每个子流程的**输入形态**与**输出形态**都不同。

```
┌───────────────────────────┐
│ 装载子流程                 │
│ 输入：磁盘字节             │
│ 输出：缓冲区（逐字节相同）  │
└─────────────┬─────────────┘
              ▼
┌───────────────────────────┐
│ 扫描子流程                 │
│ 输入：缓冲区               │
│ 手段：裸指针逐字节         │
│ 加速：尾部哨兵字节         │
│ 输出：token 序列           │
└─────────────┬─────────────┘
              │ 遇到 #include
              ▼
┌───────────────────────────┐
│ 文件栈子流程               │
│ 压栈：(当前缓冲区, 当前位置)│
│ 递归：装载被包含文件       │
│ 弹栈：回到父文件原位置     │
│ 优化：同一头文件只读盘一次 │
└─────────────┬─────────────┘
              ▼
┌───────────────────────────┐
│ 诊断位置子流程             │
│ token 存 (文件, 字节偏移)  │
│ 报错时惰性查行表 → 行号    │
└───────────────────────────┘
```

### §7 子流程 + 说人话步骤

#### 7.1 装载子流程

```
→ 拿到一个文件路径
   → 一次读完整个文件
      → 尾部补哨兵字节
         → 交给扫描子流程
```

1. **一次读完整个文件**：GCC 的 `_cpp_read_file`、Clang 的 `MemoryBuffer` 都是整读。
2. **Clang 优先 mmap，读不到才 read**；两种方式都**保证以 `\0` 结尾**。
3. **GCC 在尾部额外 pad 16 字节哨兵**。【为什么】见 7.2。
4. **本项目的做法**：`src/lex/preprocessor.cpp:Preprocessor::processFile` 用 `ifstream` 读全文，交给 `processText`。
5. **读完不加工**：缓冲区的字节与磁盘逐字节相同——**这一阶段没有任何转换**。

#### 7.2 扫描子流程

```
→ 从缓冲区首字节开始扫
   → 裸指针逐字节前进
      → 命中哨兵字节自然停
         → 不需要每次都判断"到头了吗"
```

1. **扫描循环用裸指针**：GCC 与 Clang 都持"缓冲区首指针 + 缓冲区尾指针"两个裸指针。
2. **循环体形如"逐字节前进直到引号或反斜杠或换行"**。【为什么】每个字符省一次边界判断，整文件省下几十亿次分支（10 万行量级）。
3. **哨兵字节的价值就在这里**：不需要 `if (p >= end) break;`，命中哨兵自然停。
4. **本项目目前没有哨兵**：扫描循环自己做边界检查；这是性能项不是正确性项（见 §4）。

#### 7.3 文件栈子流程

```
→ 遇到 #include "util.h"
   → 压栈：(当前缓冲区, 当前扫描位置)
   → 装载 util.h 的缓冲区
   → 从 util.h 开头继续扫
      → 读到 util.h 末尾
         → 弹栈 → 回到父文件的原位置继续扫
```

1. **压栈存两样东西**：父文件的缓冲区指针与父文件里 `#include` 那一行的结束位置。
2. **装载子文件后从它的开头继续扫**。【为什么】include 是"文本插入"，扫完子文件就该接着扫父文件的下一行。
3. **子文件结束就弹栈**，恢复父文件的扫描位置。
4. **同一头文件被 N 个源文件包含 ⇒ 只读盘一次，缓冲复用**：GCC 靠 `_cpp_find_file` 缓存，Clang 靠 `FileManager` 缓存。
5. **本项目当前没有这个缓存**（正文「启示」表里列为"中"优先级改进项）。

#### 7.4 诊断位置子流程

```
→ 扫描出一个 token
   → 只记 (哪个文件, 第几个字节)
      → 平时不查行号
         → 要报错时才回头查行表 → 得到行号
```

1. **token 不存行号**，只存"文件 + 字节偏移"。
2. **报错时才惰性查行表**（Clang 是 `SourceManager::getPresumedLoc` + 行表二分，GCC 是 `linemap` 模块）。
3. **好处**：扫描热路径上不背行号计算的行数。

### §8 异常流转表

| 异常 | 触发点 | 状态/字段变化 | 恢复路径 |
|---|---|---|---|
| 日志回吐未转义的裸换行 | 回吐路径打印已翻译的字符字面量正文时 | 一行日志被截断，后续行错位；**编译结果本身不受影响** | 打印前过一遍 `escapeCharText` |
| 字符串字面量未闭合 | 扫描子流程第 2 步，一路扫到缓冲区末尾仍未见闭引号 | 抛 `Unterminated string at <位置>`；不产出 token | 补闭引号后重新编译 |
| 空字符字面量 | 扫描字符字面量时正文为空 | 抛 `Empty character literal at <位置>（C++ 不允许 ''，见 [lex.ccon]）` | 源码写错，改掉 |
| 未知转义 | 转义翻译表的 default 分支 | 反斜杠与后随字符**原样保留**进字面量值（不报错） | 如需严格对齐 clang，扩翻译表；本项目当前明确"宽容处理" |
| 头文件被重复读盘 | 文件栈子流程第 4 步（当前无缓存） | 同一头文件被读盘 N 次；功能无影响，只是慢 | 加文件级缓存（正文「启示」表列为"中"优先级） |

### §9 瞬时状态 / 空值语义

本主题**没有持久状态**（读完就结束，不留跨调用的数据），只有一段**瞬时状态**：include 嵌套期间的文件栈。

```jsonc
{
  "文件栈": {
    "//": "阶段 4 处理 #include 时维护；每进入一个被包含文件压一层，返回时弹一层",
    "栈帧": {
      "父文件缓冲区": "std::string（父文件的字节副本）",
      "父文件扫描位置": "字节偏移（#include 那一行的结束位置）",
      "父文件名": "std::string（用于诊断与行号标记）"
    },
    "栈深": 0,          // 0 = 已经在最外层文件（栈空 = 回到最外层）
    "栈空语义": "空栈不是错误：表示当前正在处理最外层那个源文件"
  },
  "缓冲区尾部": {
    "哨兵字节": "本项目当前无（GCC libcpp pad 16 字节、Clang 保证以 \\0 结尾）",
    "空值语义": "没有哨兵不是错误：扫描循环自己判边界，只是每个字符多一次分支"
  }
}
```

### §11 接口契约

预处理器对外只有两个入口（一个是文件、一个是内存字符串），二者共用同一条管线：

| 入口 | 参数 | 返回 | 谁说了算 |
|---|---|---|---|
| 按文件处理 | `Preprocessor::processFile(path)` | 展开并合后的**完整源文本** | 文件路径指向的那个文件；路径写错直接失败 |
| 按字符串处理 | `Preprocessor::processText(src, fileName)` | 展开并合后的**完整源文本** | 调用方给的字符串；`fileName` 只用于诊断与行号标记 |

**共同约定**：

1. **两个入口的差别只有"字节从哪来"**：一个从磁盘读，一个由调用方直接给；**读完之后走的是同一条管线**。
2. **返回的是纯文本**，里面已经完成阶段 2~4（行拼接、注释剥离、宏展开、条件编译求值、include 并合），**但没有做阶段 5 的转义翻译**。
3. **`-E` 命令行开关走的就是这两个入口**：把返回的纯文本打印出来（等价 `gcc -E`）。

**为什么"文件入口"只是薄壳**：测试用 `std::string` 直喂 `processText`，
与 Clang 自己测 lexer/preprocessor 的招数一样——`clang -cc1` 的单元测试
用 `clang::MemoryBuffer::getMemBufferCopy(StringRef)` 直接从字符串构造缓冲区，
**不碰文件系统**。测试形态与真实编译器测试是同一套抽象。

### §12 否决记录

| 被否方案 | 否决原因 | 谁否的 / 什么时候 |
|---|---|---|
| 在读取阶段就把 `\n` 转成真换行 | 读取是纯字节搬运；一旦在读的时候做转换，就再也分不清"源码里本来就有换行"与"字面量里的 `\n`" | 本文主旨（正文「正确的因果链」一节） |
| 逐字符流式读源码文件 | 真实编译器都整文件读进缓冲区再扫描；文件只是灌数据的来源之一 | 正文「真实编译器怎么处理输入」一节 |
| token 里直接存行号 | 改成存"（文件, 字节偏移）"，报错时再惰性查行表；扫描热路径上不背行号计算 | 正文「诊断位置：惰性行号」一节 |
| 字符串与字符字面量各写一套转义规则 | 两者的简单转义表基本一致，字符字面量只多 `\r` `\0` `\'` 三项；分开写必然漂 | 现有实现（`src/lex/lexer.cpp:Lexer::scanString` / `Lexer::scanChar`） |

## 一句话答案

**读取不做任何转换，转义转换是某个编译器对某段文本显式执行的独立翻译阶段**。
"执行者"永远是"正在处理这段文本的那个编译器"：

| 文本里的 `\n` | 由谁转换成 0x0A | 何时发生 |
|---|---|---|
| 测试源码自身字符串字面量里的 `\n` | 编译测试的 **g++** | 测试的编译期（phase 5） |
| mycompiler 读入的源码里的 `\n` | **mycompiler 自己**（待实现的阶段 5） | mycompiler 处理字面量时 |

## 两个场景，字节级对比

### 场景 1：测试源码里的 `\n`

`test_preprocessor.cpp` 第 110 行在磁盘上的原始字节（hexdump）：

```
205c5c5c 6e 3130 20 5c6e 696e74...
   \\\   n  10    \n   i n t
```

`\\\n` 在磁盘上是 4 个 ASCII 字节 `5c 5c 5c 6e`（三个反斜杠 + n），**没有任何换行符**。

编译这个测试文件的 g++ 在翻译阶段 5 把它转成 `5c 0a`（一个字面反斜杠 + 真换行 0x0A），烧进二进制的 `.rodata`。运行时 `std::string src = "..."` 只是拷贝那些已经转好的字节——**运行时零转换**。

### 场景 2：mycompiler 用 ifstream 读源码文件

构造一个测试文件 `raw_src.txt`，内容就是字面意义的 `char *s = "a\nb";`：

```
xxd raw_src.txt:
00000000: 6368 6172 202a 7320 3d20 2261 5c6e 6222  char *s = "a\nb"
```

用 `ifstream` 读入 buffer 后，字节是：

```
63 68 61 72 20 2a 73 20 3d 20 22 61 5c 6e 62 22 3b
                          a  \  n  b
```

**`\n` 仍是两个字符 `5c 6e`，没有变成 0x0A**。读取就是纯字节拷贝。

## 正确的因果链

```
磁盘文件（原始字节，转义符号保持为多字符序列）
   ↓ read/ifstream：纯字节拷贝，零转换
缓冲区 / std::string（字节原封不动）
   ↓ 转义转换：独立的翻译阶段，仅发生在字符串/字符字面量内部
真 0x0A 生效
```

**"读"和"转"是两件独立的事**。不存在"读着读着就转了"——读取只管搬运字节，
转义是某个编译器对某段文本显式执行的步骤。

## C/C++ 翻译阶段（[lex.phases]）定位

| 阶段 | 做什么 | mycompiler 当前覆盖 |
|---|---|---|
| 1 | 物理源文件字符 → 基本源字符集（BOM/多字节处理） | 未做（假设 UTF-8 纯 ASCII 子集够用） |
| **2** | **行拼接：`\<newline>` 删除** | ✓ processText |
| **3** | **分词：源文件 → token 序列（含预处理 token）** | ✓ processText（含注释剥离） |
| **4** | **预处理：宏展开、`#if`、`#include`** | ✓ processText（递归 include） |
| **5** | **字符/字符串字面量：转义序列 → 对应字符** | **未做**——留给词法/AST 阶段 |
| 6 | 字符串字面量拼接 | 未做 |
| 7 | 预处理 token → C++ token | 未做 |
| 8 | 翻译单元合并、外部链接 | 未做 |

`processText` 注释里写"翻译阶段 2~4 总循环"——所以文本里的 `"a\nb"` 经过
你的预处理后 `\n` 仍是两个字符，**这是正确行为**。转义转换是阶段 5 的事，
归你后面的 lexer / 字面量处理实现（处理字符串字面量 token 时把 `\n` 替换成
0x0A、`\t` → 0x09、`\xNN` 等）。

## 真实编译器怎么处理输入

虽然输入是文件，真实编译器**从不逐字符流式读**——它们和 `std::string`
一样把整文件读进缓冲区，再用裸指针扫描。文件只是"往缓冲区灌数据的来源之一"。

### 装载：一次读完

| 实现 | 装载方式 |
|---|---|
| GCC libcpp | `_cpp_read_file`：read 一次读全文，**尾部额外 pad 16 字节哨兵** |
| Clang | `MemoryBuffer`：优先 mmap，否则 read；**保证以 `\0` 结尾** |
| mycompiler | `processFile`：ifstream 读全文 → `std::string` |

### 扫描：裸指针走缓冲

GCC 和 Clang 的 lexer 都持 `const char* BufferPtr + BufferEnd` 裸指针，
扫描循环形如：

```cpp
while (*p != '\n' && *p != '"' && *p != '\\') ++p;  // 逐字节不做越界检查
```

**哨兵字节**的价值：不需要 `if (p >= end) break;`，命中哨兵自然停——
每个字符少一次边界判断，整文件节省几十亿次分支（10 万行量级）。

### `#include`：文件栈

```
encounter #include "util.h":
    push (current buffer, current position) onto stack
    load util.h buffer
    continue lexing from start of util.h
end of util.h buffer:
    pop stack → resume parent at saved position
```

- GCC：`_cpp_stack_include` / 文件栈
- Clang：`Lexer::EnterIncludeFile` 递归

**关键优化**：同一头文件被 N 个源文件包含 → **只读盘一次**，缓冲复用
（GCC `_cpp_find_file` 缓存、Clang `FileManager` 缓存）。

### 诊断位置：惰性行号

token 不存行号，只存 (fileID, 字节偏移)。报错时再惰性/二分查行表：

- Clang：`SourceManager::getPresumedLoc` + 行表二分
- GCC：`linemap` 模块
